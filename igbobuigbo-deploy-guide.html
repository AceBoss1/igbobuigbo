5 Questions Before Launch

Everything you need to know to go live today — with or without Paystack, Termii, or CAC verification.

1. How is the IBI number generated?

Format: [CHAPTER_CODE]/[10_RANDOM_DIGITS]

Examples: LAG/3847291056  ·  FCT/1029384756  ·  GBR/5647382910

  • Free tiers (Student/Youth) — IBI number generated instantly on registration. No admin action needed.
  • Paid tiers — generated when admin clicks Approve in the /admin panel.
  • Chapter code = first 3 letters of chapter (e.g. Lagos → LAG, with manual overrides for FCT, Akwa Ibom, Cross River, UK, USA etc.)

2. How are pending memberships approved?

Visit https://igbobuigbo.org.ng/admin (after granting yourself admin — see Step 5).

  • See all pending paid applications with name, email, chapter, tier, payment reference
  • Click Approve → IBI number auto-generated, welcome email sent, affiliate code created
  • Click Reject → enter reason, rejection email sent to applicant
  • Free tiers auto-approve instantly — zero admin action required

3. How can the wallet work without Paystack?

Admin can credit any wallet directly — no Paystack needed.

  • Go to /admin → Credit Wallet tab
  • Enter member's IBI number, email, or Firebase UID + amount + note
  • Use for: onboarding pilot members, processing bank transfers manually, issuing bonuses
  • Members can transfer between each other once they have a balance
  • When Paystack is ready, members top up themselves via card/bank transfer/USSD

4. Where are photos and verification documents stored?

  • Profile photos — Cloudinary (configure NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME + upload preset)
  • For launch without Cloudinary — Photos simply won't upload. Card shows member initials as fallback. All other features work perfectly.
  • CAC/verification documents — Not yet implemented. Add later via Firebase Storage when CAC verification is required.
  • Member data — Firestore database (already configured)

5. Can the affiliate program start working now?

YES — affiliate works immediately on launch day.

  • Free members get their affiliateCode the moment they register (instant)
  • Paid members get their code the moment admin approves them
  • Share link: igbobuigbo.org.ng/membership?ref=IBICHUKW7X3A
  • Commission: 10% on paid registrations, 5% on marketplace sales — both editable live from /admin → Pricing tab, no redeploy needed
  • Earnings tracked in /dashboard/affiliate, withdrawable to IBI Wallet
  • No Paystack or Termii needed for the affiliate tracking to work

Step 4 — Deploy Firestore Security Rules & Indexes

This is the critical step that fixes "wallet showing ₦0" and allows members to read their own data.

Without this step: The wallet always shows ₦0, ID card may not load, and dashboard data won't display — even though the data is in Firestore. The rules file is already written for you at firestore.rules in the project root.

Install Firebase CLI (if not already installed)

npm install -g firebase-tools

Login and deploy


# Login to Firebase
firebase login

# Initialize (if first time — select Firestore only, use existing project)
firebase init firestore

# Deploy rules
firebase deploy --only firestore:rules

# Deploy composite indexes (needed for admin/affiliate/card-history queries)
firebase deploy --only firestore:indexes

Indexes take a few minutes to build after deploying — check progress at Firebase Console → Firestore → Indexes. Queries that need them will error until the build finishes.

What the rules do

CollectionWho can readWho can write
members/{uid}The member themselves + adminsThe member (own doc) + admins
transactionsOwner (where uid matches)Server only (API routes)
referrals / affiliateStatsThe referrerServer only
cardOrders / transfersThe member who owns itServer only
events / news / stats / causeTotalsEveryone (public)Server only
settings/pricingEveryone (public) — needs to show on public membership/donate pagesAdmins only, from /admin → Pricing tab

What the indexes do

CollectionFieldsPowers
eventsactive + dateHomepage upcoming events list
newspublished + createdAtHomepage news feed
cardOrdersuid + createdAtMember's card order history
transactionsuid + createdAtWallet statement chronological ordering
memberUpgradesuid + createdAtTier upgrade history

Only queries that combine an equality filter with an orderBy on a different field need a composite index — Firestore handles multi-equality (where().where()) queries natively, no index required.

Step 7 — Configure the Paystack Webhook

What this does: Every payment flow (registration, upgrade, donation, card order, wallet top-up) already verifies and records itself when the member's browser calls back after paying. This webhook is a safety net for the rare case where that never happens — the tab closes right after paying, the network drops, etc. Without it configured, the app still works fully; you just lose that safety net.

1. Get your webhook URL

https://igbobuigbo.org.ng/api/webhooks/paystack

2. Register it in the Paystack Dashboard

1

Go to Settings → API Keys & Webhooks

dashboard.paystack.com/#/settings/developer

2

Paste the webhook URL

Into the "Webhook URL" field, and save.

3

No separate webhook secret needed

Paystack signs webhook requests using your existing PAYSTACK_SECRET_KEY — the same one already in your env vars. Nothing new to generate or store.

How it decides what to do

The webhook reads the event.event field (only acts on charge.success) and routes by the payment reference's prefix — see the Reference Prefixes page for the full table. For each prefix it:

  1. Checks if the primary route (the member's own callback) already recorded this reference — if so, does nothing.
  2. If nothing was recorded yet, completes the same action the primary route would have (credit wallet, grant tier upgrade, record donation, or create card order) using the payment metadata Paystack echoes back.

Registration (IBI-REG-) is the one exception — the webhook can't safely auto-create a Firebase Auth account (it has no password to set), so instead it emails finance@igbobuigbo.org.ng to flag a paid registration that looks stuck, for manual follow-up.

Testing it

Paystack Dashboard → Settings → API Keys & Webhooks → your webhook → Send test webhook. Check your server logs for [webhook/paystack] lines, and confirm you get a 200 response back to Paystack.

2a · Chapter / Region Transfer References

Generated server-side by /api/membership/transfer — not a money-moving reference. Stored in its own transfers collection, never transactions.

PrefixExampleDescriptionFirestore Collection
IBI-CHTRF-IBI-CHTRF-MRUOXLGCChapter/region membership transfer applicationtransfers

Fixed collision: this used to share the plain TRF- prefix with wallet-to-wallet money transfers above — both generated as PREFIX-{Date.now().toString(36).toUpperCase()}, so the two were textually indistinguishable. The verify portal hard-routes any TRF-* ref to the transactions collection, so a chapter transfer ref could never be found there — and there was no admin route reading the transfers collection at all, so pending applications were invisible to admins too. IBI-CHTRF- removes the collision; /verify and the Admin Panel's Chapter Transfers tab both handle it as its own type now, and approval/rejection fires a bell 🔔 notification plus email/SMS to the member.

2b · Purse Wallet Addresses & Manual Credit References

National/regional/chapter purse wallets — lib/orgWallets.ts. Every scope gets exactly TWO wallets (main + donation), address deterministic, not random.

FormatExampleDescription
{CHAPTER_CODE}/0000000001ANA/0000000001Chapter main purse
{CHAPTER_CODE}/0000000002ANA/0000000002Chapter donation purse
{REGION_CODE}/0000000001ISS/0000000001Regional main purse (ISS=Region 1, NIS=Region 2, GDS=Region 3)
{REGION_CODE}/0000000002ISS/0000000002Regional donation purse
IBI/0000000001—National main purse
IBI/0000000002—National donation purse
IBI/0000000003—National grant purse — national scope only
ORGWLT-{timestamp}ORGWLT-1784856801943Manual admin credit to any of the above (e.g. a bank transfer received outside Paystack)

Grants are national-only by design, not by current omission. Regions and chapters do not apply for or hold grant funds independently — getOrCreateOrgWalletSet() only ever creates a grant wallet for the national scope, and creditOrgWallet() throws if anyone tries to credit a grant wallet at the region or chapter level. When grant money needs to reach a region or chapter, that's a supervised transfer OUT of IBI/0000000003 into that scope's ordinary main purse — not a grant wallet of its own. The actual transfer mechanism is Phase 2, same as auto-remittance — this just establishes where grant funds live in the meantime, consistent with the constitution's Article 8 income sources ("donations, grants and contributions") — full text at igbobuigbo.org.ng/constitution.

Address/Member Number collision: a purse wallet address is textually identical in shape to a member's IBI Number ([A-Z]{2,8}/\d{10}) — e.g. ANA/0000000001 looks exactly like a member number from the Anambra chapter. /verify handles this by trying the members collection first (existing behavior); if no member matches, it falls back to checking orgWallets by address before giving up (verifyMemberOrOrgWallet()). Balance is deliberately not shown on the public wallet result — only which chapter/region/national body it belongs to and its purse type.

Chapter donation attribution: a donation credits a chapter's donation purse either because the donor explicitly picked that chapter from the donate form's dropdown, or — as a fallback when they didn't — a best-effort match against the chapter name mentioned in their optional message field (matchChapterFromText()). No match on either → credits the national donation purse instead. Lazy creation: a chapter or region's wallet set (both main and donation) is created automatically the first time any donation or due touches that scope — most of the 43 chapters won't have wallets at all until their first transaction. /verify also provisions a wallet set on lookup if missing, for any address positively matching a real chapter/region/national code — so checking a legitimate but not-yet-used wallet (e.g. a grant reviewer verifying IBI/0000000003 before IBI's first grant) shows "exists, ₦0 received so far," not "not found." Never provisions for an arbitrary guessed code.

Public transparency vs. private balance: the public /verify result shows totalReceived — a cumulative total that only ever increases, even once Phase 2 remittances start moving money back out — never the live balance. Publishing exact current cash-on-hand for a small org's purse is a solicitation/targeting risk with no offsetting transparency benefit; the cumulative total already gives a reviewer or auditor everything needed to independently verify real financial activity. Live balance stays visible to admins only, in the Org Wallets tab.

Active Members Tab

Search all active members by name, email, or IBI number. See wallet balance, tier, status. Click Credit next to any member to jump to wallet crediting.

Credit Wallet Tab

Credit any member's wallet without Paystack:

  • Enter IBI number (e.g. LAG/3847291056), email, or Firebase UID
  • Enter amount in Naira (whole numbers only)
  • Enter a note (e.g. "Welcome bonus", "Bank transfer confirmed", "Manual payment")
  • Click Credit — instant, no Paystack needed

This records a transaction in the member's wallet history with your admin note.

Chapter Transfers Tab

Review chapter/region transfer applications members submit from their dashboard. Approve updates the member's chapter/chapterCode (their IBI Number and history stay untouched) and fires an email + SMS + in-app bell 🔔 notification automatically. Reject requires a reason, sent to the member the same way. Reference format IBI-CHTRF-..., verifiable at /verify.

Org Wallets Tab

National, regional, and chapter purse wallets — superadmin-managed for now. Every scope gets a Main Purse and a Donations wallet; the national scope additionally gets a third, Grants (IBI/0000000003) — regions and chapters don't apply for or hold grant funds independently, this is enforced in code, not just policy.

  • National and all 3 regional wallet sets are always shown; chapter wallets are looked up by chapter name (most of the 43 chapters won't have wallets until their first donation/due — created automatically on first transaction)
  • History expands a wallet's transaction ledger inline — description, reference, date, amount
  • + Credit manually credits a wallet (e.g. a bank transfer received outside Paystack)
  • Remittance percentages (chapter→region, region→national) are editable here — stored for the future auto-remittance job, not yet consumed by one

Security Tab

Look up any member by IBI number, email, or UID to place or clear a PND (Post No Debit) restriction, or restrict a specific issued card. Available to any admin — these are protective actions, not money movement, so unlike Credit Wallet this isn't superadmin-gated.

Pricing Tab

Edit registration fees and commission rates live — see the Pricing & Commission reference page for the full current values and how it works. Changes apply sitewide immediately, no redeploy.

Notifications Tab

Compose and send a notification to one of four audiences — All Members, a Specific Member (picked from the Active Members list), a Specific Region, or a Specific Chapter — see the Notifications reference page. Region and chapter sends fan out to every matching member individually; the response shows the recipient count. Appears in every recipient's dashboard bell icon.

🔒 Wallet PIN Security

Every wallet transfer now requires a session-level PIN, entered once per session the first time a member opens Wallet or Overview. Full technical detail lives in TECH_DEBT_AND_ROADMAP.md → C-01. This page is the quick reference.

Two PINs, not three. The original design included a third "flex" PIN that displayed 100x the real balance. It was dropped before being built — a balance display designed to make someone look wealthier than they are is the same mechanism used in proof-of-funds scams, and IBI's own transaction descriptions would have shown real payments as fabricated "premium VIP" amounts. Only main and duress PINs exist.

How it works

PINBehavior
MainNormal — full real balance shown, full balance available to transfer.
Duress (anti-kidnap)Shows and caps everything at 1% of the real balance. If someone is forced to unlock their wallet under coercion and "sends everything," only 1% of their real money ever actually moves — the other 99% stays completely untouched, invisible to whoever's watching.

Where PIN entry happens

Once per browser session, the first time a member opens /dashboard/wallet or /dashboard/overview — not at login, not per-transaction. Balance shows as ••••.•• until entered. The transfer confirmation modal (review recipient/amount before sending) still applies on top of this — the two are independent, not one replacing the other.

Why enforcement is server-side, not client-side

This is the one detail that matters most for the feature to actually work as a duress protection: the duress cap is enforced via an httpOnly cookie + Firestore session record (lib/pinSession.ts), never a value the client asserts in a request body. If it were client-asserted, anyone forcing a PIN out of a member could simply edit the request to claim "main mode" and bypass the entire protection. The client-side mode (lib/pinSessionClient.ts, sessionStorage) is display-only — it decides what numbers show on screen, nothing more.

Managing PINs

WhereWhat it does
/dashboard/walletContextual only — a PIN change here touches whichever PIN unlocked that specific session, never revealing whether a second PIN exists.
/dashboard/profileThe only place both PINs are visible and manageable together — change the main PIN, or set up the duress PIN (requires the main PIN to confirm).

Security details

  • PINs are hashed with Node's built-in crypto.scrypt — no new dependency added.
  • 5 wrong attempts locks PIN entry for 15 minutes. A 4-digit PIN only has 10,000 possible values — hashing alone doesn't meaningfully slow an interactive guesser down; rate-limiting is what actually matters here.
  • Duress-mode overdraft attempts get a deliberately generic "Insufficient wallet balance" error — never anything that would reveal duress mode is active to an onlooker.

Still open: the original spec had duress-mode overdraft attempts trigger a PND requiring NIN/document resubmission that silently auto-lifts on the next deposit — flagged as a compliance concern (looks like KYC enforcement happened when it didn't) but not resolved either way yet. See C-01 in the tech debt doc for the open question.

🔔 Notifications

In-app notification system — a bell icon with an unread counter in the dashboard header, backed by a single Firestore notifications collection. Full detail in TECH_DEBT_AND_ROADMAP.md → C-13.

What members see

A bell icon in the dashboard header with an unread-count badge. Opening it marks everything read and shows the recent list — transaction alerts ("Money Received", "Transfer Sent", "Wallet Topped Up") fire automatically from the wallet transfer and top-up routes.

Admin broadcast

/admin → Notifications tab — compose a title, message, and optional link, then send to all members or one specific member (picked from the Active Members list). Same mechanism planned for a future IBI Ads push feature — just a different type and richer audience targeting later, no schema change needed.

This is in-app only — not real OS-level push yet. The bell works immediately for every member with zero setup. Actual push notifications (the kind that show up outside the browser tab) need Firebase Cloud Messaging, which requires generating a VAPID key pair in the Firebase Console — a step only Emmanuel can do. The data model doesn't need to change when that's added; it's an additive follow-up, not a rebuild.

Server-routed, same lesson as pricing

Every notification read/write goes through a server route (app/api/notifications/*), never a direct client Firestore call — the same lesson learned the hard way from the pricing panel bug (see Known Gaps C-11): anything that depends on Firestore rules being correctly deployed is one missed firebase deploy away from silently failing.
